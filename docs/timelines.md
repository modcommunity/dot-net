# Timelines: the clock and the interpolator

## Three timelines, not one

The thing most often got wrong, and the reason `DotNetClock` is the first file to read. At any instant a client deals with three tick numbers:

```
  render tick        server tick        input tick
  (behind)           (estimated)        (ahead)
  ────────────────────────●────────────────────────>
       ↑ interpolate           ↑ predict
```

- **Input runs ahead.** A command for tick N must be in the server's hands before it simulates N. Running level with the server means every command arrives late.
- **Render runs behind.** Interpolating needs both bracketing snapshots to have arrived.
- **The server tick is estimated**, never known.

## Drift and catch-up

- **A client ahead of its target is smoothed by scaling tick duration**, not by jumping the tick number: snapping teleports every predicted object and re-runs applied inputs (`MAX_DRIFT_RATE`).
- **Behind is not drift.** A client behind its target stamps every command for a tick the server has already simulated, and the server discards each as late. The engine drops every physics step past its cap in a frame, so every stall (a scene loading, a shader compiling on first draw, both of which a browser does for seconds on a first connect) put the clock behind by the stall's length, until the clock learnt to read the wall clock ([time the engine drops](#time-the-engine-drops)). Smoothing that at the drift rate turned a half-second hitch into ten seconds of a player who could not steer. So a client behind by more than the input margin (`catch_up_threshold_ticks()`) **jumps forward at once**: the ticks jumped over are never sent and the server repeats the last command for them, as for a lost packet. Prediction has to replay across that hole; see [prediction.md](prediction.md#reconciliation).
- **Past `SNAP_THRESHOLD_SECONDS` it snaps** either way, because a suspended tab is not drift. It is a **duration**: as a tick count, 60 ticks was one second only at 60 Hz, and a 128-tick server snapped at 0.47 s and threw a predicted state away for every half-second hitch.
- **A game-driven server's clock follows `server_tick(tick)`.** With `auto_tick = false` (every game here) nothing else advances it; without it `clock.tick` read 0 for the server's life and every HELLO told a joiner to sync to tick 0.

## The input lead the server reports

**Once the server says how early a client's commands reach it, the input timeline is steered by that, not by the round trip** (2026-10-11, `FEATURE_INPUT_LEAD`). Before, the lead was half the round trip plus a margin, and the round trip a game feeds is ENet's smoothed one (an eighth of each new sample, a ping every half second) through a median of sixteen: when the path got 30 ms slower each way, the lead followed over seconds and every command meanwhile reached the server after its tick. game-arena's `headless_feel` (40 to 70 ms each way): 75-153 commands late in 5 s, the last 2.9-4.1 s after the change, 38-76 prediction corrections, the eye going backwards on 56-111 frames. Now: 0 late, 0-2 corrections, 0 backwards, in six runs of six.

- **The server measures arrival, per peer.** `DotNetInput.Buffer.push` takes, for each input newer than any before it, its tick less the next tick to simulate: 0 is just in time, below 0 late. A resent copy says nothing and is not measured. The least of a snapshot period, with the input tick it was measured on, goes in every part of the next snapshot to that peer ([wire.md](wire.md#the-input-lead)).
- **The client measures it against the moment the command was sent, not against now.** `DotNetClock` remembers, for each tick it produced, how far its timeline stood ahead of local time (`_local_ticks`: the deltas it was handed, never scaled by the drift) at the end of that frame. The lead a report says was needed is that, less the arrival lead, plus `lead_slack_ticks` (`DotNetConfig.input_lead_slack_ticks`, 2). A report a round trip old already counts every correction made since its command was sent, so the clock never corrects twice; and nothing about the downlink is in it, which is the receive timeline's business.
- **The lead is the most any report in the last second needed** (`LEAD_WINDOW_SECONDS`): the margin is over the worst arrival seen, so jitter is covered by measuring it, which the clock's own jitter estimate never did on ENet (it reads about zero).
- **Steered every frame, never jumped for a small deficit.** Ticks run up to `LEAD_RAISE_RATE` (12%) short while the lead is short and up to `MAX_DRIFT_RATE` (5%) long while it is long, at a tenth of the error a tick. A deficit too big to gain in `LEAD_SMOOTH_SECONDS` (0.5 s, about 60 ms of lead) is a stall, not a slower link, and jumps as a catch-up did. A different session still snaps.
- **Recorded at the frame's end, with the fraction.** The position steered is the tick plus the fraction of the next already run; the lead recorded for a command is the same position, less the ticks produced after it in the frame. Recorded as the bare tick, it was up to a tick behind what was steered and the clock settled a tick short of the slack asked for.
- **The receive timeline is held to real time while the clock runs fast.** It advances by the same ticks as the input timeline, so ticks 12% short would carry it ahead of the snapshots, where it comes back a tick per `SETTLE_SAMPLES` and everything remote extrapolates meanwhile. What the drift adds (`_receive_excess`) is taken back a tick at a time through `receive_slip`. `netcode_demo` at 20 snapshots a second: 6 ticks past the newest snapshot without it, 4 with it, the control 3.
- **Slips are taken up at least twice as fast as the drift makes them** (`_slip_recovery`). `SLIP_RECOVERY` (0.1) was twice the most `MAX_DRIFT_RATE` makes; at 8% fast the slips piled up to the clamp and the tick past it was drawn as a jump (game-arena's `headless_feel` at 20% loss, 3-5 cm in one frame).
- **Commands must be stamped from `input_tick()`**, as every game's client does: a report is about a command the clock stamped. A host that stamps its own lead (every game's `headless_net` harness stamps `_tick + 2`) hears, in each report, that it needs a tick more than the clock has given, whatever it gives; such a host clears `FEATURE_INPUT_LEAD` from its client's `messages.features` (game-playground's does). And the lead is capped at the round trip's own lead plus another flight time plus `LEAD_CAP_TICKS` (4), so a clock fed reports it cannot use stops there instead of running away (`netcode_demo`: 7 ticks ahead capped, 29 uncapped in 10 s). Measured leads sit well under the cap.
- **Never behind the server, whatever the reports say** (`floor_count()`). A clock steered by the reports at or behind the newest snapshot it holds (`received_tick()`) is stamping commands the server has already simulated, and every report about them arrives a round trip after the fact. `sync_from_server` jumps it to the reported lead, or past the newest snapshot by the margin if that is further. The floor adds no flight time and the jump uses no round trip: the round trip a game measures around a stall holds the stall (g2gfast joining at 128 on a 100 ms link: 749 ms), and a floor built from it fired on every join and held the clock 600 ms ahead. Before 2026-10-14 this path returned without looking, and a client that fell behind faster than the reports could say stayed behind.
- **A different session still snaps, when the round trip agrees on the direction.** The reported lead alone can be a stall stale; snapping back to it undid the floor on every snapshot.
- **Before the first report, and against a server that does not send one, nothing changed**: the round trip and the margin, as in [drift and catch-up](#drift-and-catch-up).

## Time the engine drops

**`DotNetClock` follows the wall clock, not only the deltas it is handed** (2026-10-14, [history](history.md) #31). The engine runs at most `max_physics_steps_per_frame` physics steps a frame and drops the time past that without a word: 8 steps are 133 ms at 60 Hz and 62.5 ms at 128. `advance` is handed each step's delta, so local time, the input tick and the receive timeline all ran slow by exactly what was dropped. Before the reports, the absolute catch-up on the next snapshot hid it. With the reports steering, every report about a command sent after a drop said how much later it had to be, a round trip later, and a client that kept dropping (a browser's first visit: seconds of loading and shader compiling, then slow frames) stayed behind by the drift times that delay. game-g2gfast's players stood on the spawn pad: against a real server on `surf_mesa`, 150 ms frames over a 100 ms round trip at 128 ticks, every command late and the player never moved.

- **Measured from the engine's own numbers** (`Engine.get_process_frames`, `get_physics_frames`, `physics_ticks_per_second`, `max_physics_steps_per_frame`, `Time.get_ticks_usec`), at a frame's first physics step (`note_engine_frame`) and before each snapshot is read (`note_engine_time`). The steps a frame runs cover the wall time up to that frame's start, so the gap up to the previous frame's start is exact once a frame begins, and a frame that drops runs exactly its cap, so the gap up to now less a whole cap is dropped for certain. `DROP_MARGIN_STEPS` (3) covers the engine's accumulator and jitter fix: a clock whose engine keeps up credits nothing and does exactly what it did before (`netcode_demo` runs both).
- **Credited to local time, the input tick and the receive timeline together** (`_credit_dropped`), because the steps that would have moved all three never ran. Before the first report nothing else moves the tick until the next snapshot; left on the receive timeline only, the cap on the lead sat a stall back.
- **Seen before the snapshots that followed it are read.** A host reads its packets in its frame's process, where a stall happens too; credited only at the next frame's first step, the drop was added again on top of what those snapshots had already moved, and the clock ran a stall ahead and snapped back.
- **Never while a server's clock lives in the same process** (`DotNetClock.server_in_process()`, a count of authority clocks). The engine's numbers say this process stopped, not that the server kept going, and a server in the same process (a listen host, a harness running both ends) stopped too. Credited anyway (v0.1.8), a 0.38 s hitch on joining put dot-server-deploy's `lookatme_client` first player 22 ticks ahead of the server beside it, given back at `MAX_DRIFT_RATE` over seven seconds, and the next section's walk came out 1.1 to 1.8 m against more than 2. Crediting only what the server's snapshots confirmed was tried and dropped: they confirm a drop a snapshot period late at best, and a credit trailing a few ticks every frame was either asked for again by the reports (commands 80 ticks early after a join hitch) or, corrected for, steered every command of a client on steady slow frames late.
- **After a stall (a drop past `LEAD_SMOOTH_SECONDS`), the last two frames' commands are recorded as that much less far ahead.** A report measures a command from when it was produced; one produced before a three-second hitch and sent after it asked for the hitch as lead on top of the credit, and the clock jumped a stall ahead and snapped back. Two frames, because a host may flush a frame's packets at the next frame's poll. A shorter drop is a slow frame that will come again, and its send delay is a frame the lead must cover: moving those back steered a client on steady slow frames late by the drop.
- **The receive timeline counts one late sample a frame**, and goes back more than a second only after a whole window of frames whose samples keep pace with local time. The snapshots a stall held up arrive behind a timeline the stall was credited to, oldest first, in one burst or drained over many frames; counted one by one they were windows of a slower path, and anchored to one of them the timeline went back the whole stall and the clock snapped back with it. A stall's credit closes the window open across it: one spanning the credit read as samples keeping pace a second behind. "A frame" is a step of `advance`, not of a credit, which moves local time inside one frame.
- **Only while the engine drives the clock**: one `advance` a physics step, the latest included, at a time scale of 1, while `follow_engine_time` (default on). A harness that sets `tick` itself and feeds snapshots in one long loop is a stall by the wall clock; followed, it moved the clock under game-arena's `headless_net` and a wall route came out 0.19 m off. A call outside a physics step, or a second in one, drops the reference. A test that drives the engine's numbers by hand clears `follow_engine_time` and calls `note_engine_frame` and `note_engine_time` itself.
- **The reference frame's own steps are not counted**: they cover the time up to its start. Counted, a reference taken on a frame catching up put the engine eight steps ahead of the wall for good and every later drop came out 133 ms short.
- `lost_seconds()`, `lost_count()`, `floor_count()`; `describe()` has `floors` and `lost_ms`.

Measured against a real g2gfast server on `surf_mesa`, a separate client process over a 100 ms round trip, forward held only after the stalls: commands the server discarded as late in 10 to 14 s (before is v0.1.7's clock; game-g2gfast's own cap is a quarter second of ticks):

| Client frames | 60 Hz before | 60 Hz after | 128 Hz before | 128 Hz after |
| --- | --- | --- | --- | --- |
| 150 ms, the engine's default cap of 8 | 400 | 0 | 1294, never left the pad | 0 |
| stalls of 4 s and 2.5 s, then 60-150 ms, cap 8 | 115 | 7-10 | 1404 | 0 |
| the same, the game's cap | 48 | 10-12 | 140-158 | 36-42 |
| stalls of 3 s and 5 s, then 150-400 ms, the game's cap | 416 | 7-8 | 1100 | 1-3 |
| 14-18 ms | 22 | 0 | 47 | 0 |

What is left after a stall on random 60-150 ms frames is the frames themselves: a command waits for the rest of its frame to go out, and a frame longer than any in the last second is late by the difference.


## The receive timeline

The timeline the clock walks is the RECEIVE timeline: `received_tick()`, the newest snapshot tick as the quickest recent packets place it. `server_tick()` is that plus the flight time (`one_way_ticks()`).

- **It moves between packets.** `advance()` walks the estimate forward with the local clock and `sync_from_server` re-anchors it. Set only on arrival, the rendered tick was a step function of arrivals: at 20 Hz snapshots and 144 Hz rendering, six frames in seven drew the previous one. A stall that drops ticks drops them from both timelines, or the input lead would appear to have grown by the stall and the next sample would correct it as drift.
- **One late sample a frame.** A burst read in one frame is one arrival time ([time the engine drops](#time-the-engine-drops)); a window of frames more than a second behind whose samples keep pace with local time is a different session and anchors back, never one sample and never a backlog draining.
- **It follows the quickest arrivals.** Re-anchoring to `sample + one_way` on every snapshot moved the timeline back with every slow packet and forward with the next: a remote player drawn half a metre back and forth with every position correct (the truth moves back with the time it is sampled at, so no position check can see it). Now it moves forward at once to a sample ahead of it, ignores one behind it, and goes back one tick only after a whole `SETTLE_SAMPLES` (16) of samples all behind it. Following the quickest packets also puts the input lead about half the jitter higher, which is what stops late commands on a jittery link.

## The render time

- **The interpolation buffer is in snapshots.** `DotNetConfig.interpolation_buffer` says "snapshots of delay" and `_delay_snapshots` holds it. `delay_ticks()` (`_delay_snapshots * ticks_per_snapshot()`) is the one conversion and the only thing `sample()` subtracts. It lives in the interpolator, not the manager, because `sample()` and `apply()` are public and take a tick. It uses `ticks_per_snapshot()` (the integer the manager sends on: 6 at 128/20, not 6.4), so "two snapshots" means two that arrive; `delay_ms()`, `_adapt` and `DotNetConfig.interpolation_delay()` use the same. `delay_snapshots()` is the old number under an honest name; `delay_ticks()` is what `DotNetHistory.client_view_tick` wants.
- **The render time is `received_tick() - delay_ticks()`**, not `server_tick() - delay`. Counting back from the server tick spent part of the buffer waiting for a snapshot still in the air, and on a 120 ms round trip nearly every frame was extrapolated. It never shows on a loopback, where the flight time is zero. `DotNetHistory.client_view_tick` (`current - one_way - delay`) always assumed this.
- **The interpolator is fed what the server said** (`DotNetBehaviour.received_values()`, the receive-side baseline), never the properties, which between snapshots hold the interpolator's own last blend. Fed its own output, anything that changed once and stood still froze part of the way there.
- **The buffer is sized from how late snapshots arrive** (2026-10-10). The manager calls `note_lateness(tick, clock.received_tick())` on every applied snapshot: how far behind the receive timeline it came, in ticks. The buffer has to cover one interval to the snapshot after the render time, the 95th percentile of that lateness over the last 64 arrivals, and one more interval if any of those 64 never arrived (`_adapt` takes the larger of that and the old arrival-gap estimate). A tick more for the frame's fraction would be exact and is left out: it cost every clean link a tick (game-arena steady: 4.1 ticks with it, 3.0 without, 2.5 before) to cover what the bounded extrapolation draws within millimetres. The gap estimate alone (one interval plus two mean deviations of the gap between arrivals) came to about two thirds of what a 30..80 ms link needs. Measured over real ENet through the relay at 5% and 20% loss, 30..80 ms: game-g2gfast's `headless_feel` (128 ticks, 32 snapshots) extrapolated 7.5-11% of frames (37% in the window after a steady link turned jittery), now 0.7-2.4%, worst error 3.5 cm against 4.6-8.3; game-arena's `headless_lossy` (64 ticks, 32 snapshots) 13-14%, now 0.3-2%. The cost is latency under loss: 15 ticks (117 ms) at 128 where it was about 9-11, and 8 (125 ms) at 64 where it was 5 (80 ms).
- **The drawn buffer follows its target at `GROW_RATE` (0.2), never jumps to it.** The render time is the receive timeline minus the buffer, so a buffer that grows from 1.3 snapshots to 2.2 at once draws every remote entity 3.6 ticks back in one frame: the same `headless_feel` measured the render time stepping back 11 times in eight seconds, by up to 3.45 ticks, when a steady link turned jittery. `_target_snapshots` is where it is heading (grows at once, shrinks 1% an arrival, as the buffer itself did), `_delay_snapshots` is what is drawn, and `advance(elapsed)` (called by `DotNetManager.interpolate_frame`, once a frame) moves one toward the other by at most a fifth of the time that passed: a remote player slowed to 80% for a moment instead of one sent backwards. A host that never calls `advance` gets the old behaviour, the buffer following its target at once. `netcode_demo`'s *the buffer growing* plays a link that turns late, tick by tick: armed with `GROW_RATE` 1000 the render time steps back 3 ticks, and without the lateness term 115 of 256 ticks extrapolate.
- `sample_count()`, `stall_count()` and `extrapolation_count()` (with `reset_counts()`) exist so a suite can assert nothing extrapolated, not just read it in `describe()`.

## Drawing through slips

A client's timelines move in whole ticks in three places, and anything drawn from them jumped with them. Found by game-arena's `headless_feel`, which judges each rendered frame against the motion it was drawn on (2026-10-11); `netcode_demo`'s *drawing through slips* plays each at 144 Hz against 64 ticks beside its control.

- **A physics frame that ran no tick, or two.** The engine's fraction is through a physics frame, a fraction through a tick only while each physics frame runs one. A drifting clock stretches or shrinks its ticks (up to `MAX_DRIFT_RATE`), so now and then one runs none and a later one two, and drawn at the engine's fraction the frame after went back over the step it drew or moved double (game-arena: 4 to 8 frames in 5 s, 10 to 16 cm off, at 60 Hz and through 5% loss). `advance` counts the tick a frame gained or lost into `_slip`, and **`render_alpha()` is the engine's fraction plus what is left of it**, taken back at `SLIP_RECOVERY` (a tenth of a tick per tick: twice the most drift can make, and a tenth slow or fast reads as nothing). It runs from -1 to 2 for a moment, so a renderer drawing between its last two ticks extrapolates along the last step past 1 and needs the tick before below 0. `interpolate_frame` uses it by default. Tried first and worse: the clock's own accumulator, which is continuous but sits up to a tick past the newest tick all the time and extrapolated through every wall (474 of 719 frames off at 144 Hz).
- **The receive timeline re-anchoring**: forward at once to a quicker sample, back one tick after `SETTLE_SAMPLES` slower ones. The timeline and the buffer sizing still move at once; **what is drawn follows at `RECEIVE_RECOVERY` (20%, the buffer's own `GROW_RATE`) through `receive_slip()`**, which `interpolate_frame` adds. Drawn as it was, every remote entity jumped a tick at that moment: 2 to 5 frames a window drawn behind the one before, after a link's delay changed.
- **A resumed stream after an extrapolation.** The line guessed past the newest snapshot was off by however far the entity turned, and the next snapshot snapped it back (17 to 32 cm in one frame through 20% loss). **`apply` measures the jump exactly** (what the last frame's extrapolation would draw now, less what is drawn now) and eases it out over `RESUME_EASE_SEC` (60 ms, exponential); a jump past `RESUME_EASE_MAX` (1.5 m) is a teleport. Positions only, and only once a host drives frames through `advance`. `sample()` is untouched: lag compensation and suites read the truth.

## _net_interpolated

`DotNetInterpolator.apply` writes the smoothed value of every property declared `interpolated()` and then calls `DotNetBehaviour._net_interpolated(render_tick)`. That call is the whole point: the obvious hook, `_net_state_applied`, fires when a snapshot arrives, a few times a second, and a game with only that hook moves every remote entity in 20 Hz steps while the interpolated value sits in a property nobody reads. The symptom is an interpolator that appears not to work.

It deliberately carries none of `_net_state_applied`'s bookkeeping: its tick is a render tick, and recording it as the newest state applied would make reconciliation rewind to a tick the server never sent. A predicted entity is never notified, because writing interpolated state over a prediction fights the predictor every frame.

## Open: jitter and loss

Found by game-arena's `headless_lossy` through the UDP relay, not fixed:

- ~~**A link that slows mispredicts for seconds.**~~ The server reports the input lead since 2026-10-11: see [above](#the-input-lead-the-server-reports).
- **The clock's jitter is always about zero on ENet**, so `adaptive_margin` never widens the margin. It is the spread of the round-trip samples it is fed, a game feeds one per snapshot, and the number it feeds (ENet's smoothed round trip, or a two-second heartbeat) barely moves. It matters only before the first report and against a server without `FEATURE_INPUT_LEAD`, where the receive-timeline filter covers jitter at the price of an input lead 2-4 ticks over what the transit needs (game-arena at 40 ms each way: 8 ticks from the round trip, 4-5 from the reports).
- ~~**The adaptive interpolation buffer is sized for jitter, not for loss.**~~ Sized from lateness and loss since 2026-10-10: see [the render time](#the-render-time).
